# 模板启动诊断原型（THROWAWAY）

> 这是用于回答规格交互问题的可抛弃原型，不是扩展生产代码，不应直接打包或发布。

## 要回答的问题

根会话首次发现代理模板时，能否在不暴露模板正文或其他秘密的前提下，一次说明哪些候选模板配置无效，同时让合法模板继续正常参与发现？

## 运行

仓库没有现成任务运行器，直接使用已安装的 Node.js：

```powershell
node .scratch/pi-subagent-spec/prototypes/template-startup-diagnostics-throwaway/demo.mjs
```

脚本输出一条根会话启动警告及完整的有效模板目录，用于人工检查“错误可见、坏模板不可发现、好模板不受影响”三个结果。

加入 `--reload` 可演示根会话重载后目录替换仅影响未来创建，既有节点不会被回溯修改：

```powershell
node .scratch/pi-subagent-spec/prototypes/template-startup-diagnostics-throwaway/demo.mjs --reload
```

加入 `--directory-error` 可演示一个模板来源目录无法扫描时，另一来源仍可提供模板：

```powershell
node .scratch/pi-subagent-spec/prototypes/template-startup-diagnostics-throwaway/demo.mjs --directory-error
```

## 原型结论

- 每个候选文件独立校验，一个模板配置无效不影响其他模板。
- 根会话首次发现结束后最多显示一条汇总警告；没有配置错误时不显示警告。
- 每项诊断只包含模板来源、文件名和安全的简短原因，不包含模板正文、环境变量或解析对象。
- 无法读取的文件、失效的符号链接和无法解析的 frontmatter 同样按无效模板处理；仅展示安全类别，不展示底层路径或异常堆栈。
- 配置无效的候选文件不进入有效模板目录，也不出现在父代理可见的模板说明中。
- 已获信任的无效项目模板仍遮蔽同名合法用户模板，不会静默回退到用户模板。
- 被合法项目模板遮蔽的无效用户模板仍显示在启动诊断中，但不影响该模板标识的创建。
- 模板目录缺失是正常空来源；目录无法扫描只形成来源级诊断，不阻断另一来源的有效模板。根重载时仍发布本轮部分新目录，不保留失败来源的旧模板。
- 子代理复用根会话得到的目录和诊断结果，不重复显示启动警告。
- 真实扩展应使用 `ctx.ui.notify(..., "warning")`；它只展示给用户，不创建消息、会话条目或模型上下文。print/JSON 无 UI 模式中该调用是 no-op，且不另设可见回退通道。
- 根会话 `/reload` 后会重新发现并替换后续创建使用的目录，若仍有问题则再次显示一条当前汇总警告；不做文件监听，既有节点也不回溯更新。

## 有意不做的内容

- 不决定运行时重载后是否再次显示警告。
- 不决定模板文件或目录读取失败时的诊断方式。
- 不实现真实 YAML 解析、Pi UI 调用、模板覆盖或子代理创建。
