# Spec: 渲染帧成本削减（工具渲染纯文本组件）

Status: ready-for-agent

## Problem Statement

父会话用户在使用子代理编排时，只要会话变长、子代理变多，pi 的 TUI 就会变得不可用：

- 在输入框敲一个字/删一个字有明显延迟（实测：**单次按键约 290 ms**，即打字上限约 3.4 键/秒；按住键连发会积压十几倍输入）。
- 鼠标滚轮滚动同样卡（实测：**单帧约 272 ms**），滚一格要等小半秒。
- 但**完全空闲时进程 CPU 为 0**：没有任何后台轮询或自发光重绘。也就是说这不是"空闲卡"，而是**"每一次交互都要付一次整帧渲染成本"**。

这个成本与扩展的产出直接相关：子代理越多、`send_message` / `final_report` / 工具调用越多，父会话 transcript 里需要渲染的文本就越多，单帧就越慢。用户实际被迫做出的妥协是"少发长消息、少开长会话"，而不是继续工作。

CPU profile 取证（56 s 采样，宿主任意一帧都全量重渲染整份文档）显示，单帧渲染耗时中：

- **约 79% 消耗在扩展自己的纯文本渲染组件里**（工具调用/结果的渲染载体），而 final_report 的 custom message 渲染只占约 2%。
- 其中绝大部分是"整串宽度测量"与"逐字素折行"这一条链路：组件每帧都对同一份文本**重新净化 + 重新折行**，且折行循环对**每一个字素**都调用一次"整串宽度测量"，而该函数内部又对整个入参跑一遍 Unicode 字素切分——即每个字素多付一整轮字素切分与对象分配。
- 现有文本量级：一个中大型父会话里工具调用参数文本可达 6 万字符，其中单条 `send_message` 正文最大 8 千字符；为了在界面上显示 7 行，这些正文每帧都被完整折行一遍。

用户视角的问题陈述：**"我只是在输入框里敲字，凭什么要等 0.3 秒？"**

## Solution

让工具调用/结果的渲染在"内容没有变化"的帧上**零成本**，并让"内容发生变化"的那一帧也不再对同一段文字重复付 Unicode 字素切分的代价：

1. **渲染结果缓存**：纯文本渲染组件按（可用宽度、内容版本）缓存上次渲染出的行数组；内容更新时版本递增并丢弃缓存；宿主发出的失效信号也丢弃缓存。
2. **折行改走字素宽度**：折行循环已经拿到单个字素，直接用字素宽度函数测量，不再绕道"整串宽度测量"（等价变换，输出不变）。
3. **宽度计算记忆化**：码点宽度按码点做记忆化；整串宽度加有界 LRU（与宿主 `visibleWidth` 同类做法）。
4. **净化与固定宽度前移**：文本净化、前缀/后缀宽度这类只依赖内容的计算，在内容更新时做一次，随版本一起缓存。

硬性要求：**渲染输出逐字节不变、用户可见文案不变、缓存大小有界、不改变任何布局或折叠行为**。目标是从"单帧约 290 ms"降到"单帧约 60 ms 量级"，剩余部分是宿主的每帧全量渲染（不在本 effort 范围）。

## User Stories

1. 作为父会话用户，我想在长会话里敲字时字符立刻上屏，以便不必等待 0.3 秒才看到自己输入的字符。
2. 作为父会话用户，我想按住键连发时输入不积压，以便能像在其他编辑器里一样连续打字。
3. 作为父会话用户，我想用滚轮平滑翻阅长 transcript，以便不因每次滚动等半秒而放弃回看历史。
4. 作为父会话用户，我想在子代理很多、transcript 很长时仍然可用，以便不必为了流畅而缩减我的工作方式。
5. 作为父会话用户，我想在发出较长 `send_message` 正文后界面不明显变卡，以便长消息不会变成"性能惩罚"。
6. 作为父会话用户，我想在工具有部分结果持续更新（partial）时界面仍保持响应，以便观察执行进度不卡住。
7. 作为父会话用户，我想在工具结果更新后立刻看到正确内容（而不是旧缓存），以便缓存永远不会让我看到过期信息。
8. 作为父会话用户，我想在切换主题后看到正确的配色，以便缓存不会残留旧颜色。
9. 作为父会话用户，我想在调整终端宽度后看到正确的重排结果，以便缓存不会在宽度变化后返回旧布局。
10. 作为父会话用户，我想在折叠/展开长工具结果时看到正确的行数提示与内容，以便缓存不影响折叠语义。
11. 作为父会话用户，我想优化前后看到**完全一致**的界面文本，以便这次性能修复对我零风险、零感知。
12. 作为父会话用户，我想包含中文、emoji、组合字符与百分比宽字符的文本仍然正确对齐与截断，以便性能优化不破坏东亚文本显示。
13. 作为父会话用户，我想包含控制序列注入的不可信文本仍然被净化，以便性能优化不打开终端注入的口子。
14. 作为子代理会话用户（子会话自身的 TUI），我想同样受益于这项优化，以便子代理会话里的工具渲染也不拖慢界面。
15. 作为扩展维护者，我想缓存的失效条件由"内容版本 + 宿主失效信号"两个明确入口决定，以便不会出现难以复现的脏渲染。
16. 作为扩展维护者，我想缓存是"每组件只保留最近一次宽度结果"的有界形态，以便长会话不会因缓存而内存膨胀。
17. 作为扩展维护者，我想有一条"优化前后输出逐字节等价"的回归测试，以便未来改动不会悄悄改变渲染结果。
18. 作为扩展维护者，我想有覆盖"幂等渲染 / 更新后立即可见 / 失效后重算 / 宽度变化重排"的单元测试，以便缓存语义被钉住。
19. 作为扩展维护者，我想宽度原语（码点宽度、整串宽度）保持纯函数等价，以便记忆化不会成为正确性风险。
20. 作为扩展维护者，我想这次改动不触碰活动面板、活动查看器、树 widget 的渲染路径，以便把变更面压到最小。
21. 作为扩展维护者，我想在改动后用同一套 profile 采样复测，以便用"单帧耗时 / 热点占比"作为验收证据，而不是靠主观感受。
22. 作为扩展维护者，我想性能验收标准写成可复现的数字（单次按键的毫秒数、热路径占单帧的比例），以便下一个 agent 能独立确认目标达成。

## Implementation Decisions

**范围**

- 只改两处模块：**工具渲染模块**中的纯文本渲染组件与其折行辅助；**UI 表面宽度模块**中的宽度原语。父会话与子会话共用这两处，故两边同时受益。

**缓存（决策主体）**

- 纯文本渲染组件的渲染输入只有四项：内容行数组、主题、渲染选项、入参可用宽度。前三项只能通过既有的 `update(...)` 入口整体替换，第四项是调用参数——因此缓存键取 **（可用宽度, 内容版本号）** 即完备。
- 内容版本号在 `update(...)` 时递增；`update(...)` 会整体替换内容、主题与选项，因此主题/选项变化自然也走版本失效，无需额外键。
- 组件的 `invalidate()` 当前为空实现，本次实现为**丢弃缓存**。这样宿主在主题切换、终端配色变化等场合发出的全树失效信号同样能清掉缓存；宿主重建组件（`updateDisplay` 路径）则由版本号覆盖。两条失效路径互不依赖，都各自足够。
- 缓存形态：每组件只保留**最近一次**（宽度 → 行数组）的结果，不保留多宽度的历史；命中即返回同一数组引用（与宿主纯文本组件、Markdown 组件的做法一致）。
- 缓存不跨组件共享，不做全局 memo（避免引入跨实例失效耦合）。

**宽度原语**

- 折行辅助在逐字素循环中直接使用**字素宽度函数**。理由：当入参恰好是单个字素簇时，"整串宽度测量"必然只切出一个等于入参的段，因此两者数学等价，结果是逐字节相同的。
- 码点宽度做按码点的记忆化（Map，键为码点值）。码点空间小、命中率高，且函数是仅依赖码点的纯函数。
- 整串宽度加有界 LRU（容量与宿主同量级，约 500 条）。注意：折行路径传入的是单字素，会让 LRU 迅速轮换，所以 LRU 主要服务"整行测量/截断"场景，不承担折行路径的加速职责——折行路径的加速来自上一条。

**净化前移**

- 文本净化（前缀、正文、后缀、溢出提示段）以及前缀/后缀的显示宽度属于"只依赖内容"的计算，随 `update(...)` 预计算并随版本缓存；渲染时只做着色与拼接。
- 该前移同时被上面的结果缓存覆盖：内容不变时不会进入该路径。

**兼容与约束**

- 不改任何用户可见文案、行数上限、折叠提示的语义与数值。
- 不做"折行早停"（那会改变 `… (N more lines, …)` 提示里的行数），明确排除（见 Out of Scope）。
- 缓存必须无副作用：命中与未命中的输出必须逐字节相同，可由回归测试验证。
- 内存上界：每个组件最多缓存一份行数组；宽度原语 LRU 有固定容量上限。

**验收阈值（取自 profile 取证）**

- 热路径（纯文本组件渲染）在单帧中的占比应从约 79% 降到个位数百分比。
- 单次按键的 CPU 耗时从约 290 ms 降到约 60 ms 量级（剩余为宿主每帧全量渲染）。

## Testing Decisions

**什么是好测试（本仓库口径）**

只通过公共渲染入口断言**外部可见输出**：给定内容与宽度，返回的行数组内容、行宽、以及折叠/截断后的文本。不断言内部字段（缓存命中标志、版本号、Map 内容）——这些是实现细节，重构时会变。

**测试模块与 seam**

- 唯一 seam：**公共渲染入口返回的组件 `.render(width)`**（现有工具渲染测试已经全部走这个 seam：既有的 `renderAgentToolCall` / `renderAgentToolResult` 返回组件的行断言）。不新增 seam。
- 宽度原语的等价性也通过同一 seam 验证（用含中文/emoji/组合字符/超长行的输入按窄宽度渲染，断言每行不超过宽度且字符不丢失），不为纯函数单独开新 seam。

**必须先有的回归基线（本次关键）**

- 等价性测试：在测试内保留一份"未优化"的参考实现（或在测试里对一组固定输入预先生成期望行数组快照），断言优化后的渲染输出与参考实现**逐字节一致**。覆盖：CJK、emoji（含 ZWJ 序列）、组合字符（泰文/老挝文 AM 类）、宽字符、控制序列注入文本、空文本、超长单行、含前后缀与溢出提示的行。
- 语义测试（覆盖缓存失效）：
  - 幂等：同一组件、同一宽度连续渲染两次，结果深度相等（且不重复产生不同字符串）。
  - 更新可见：`update(...)` 换内容后立刻渲染，必须反映新内容（不得返回旧缓存）。
  - 失效语义：主题样式可观察地变化（例如让测试主题在两次 render 之间改变输出）后调用 `invalidate()`，再次渲染必须使用新样式。
  - 宽度变化：同一组件用不同宽度渲染，各自满足 `每行显示宽度 ≤ 宽度`，且与"无缓存基线"一致。
- 既有测试作为回归网：现有工具渲染测试集（约 56 KB 用例，覆盖各工具的调用/结果渲染、折叠、耗时后缀、宽度约束）必须全绿且无需修改期望值——如果它需要改期望值，说明输出变了，属于违约。

**Prior art**

- 工具渲染测试：通过 `renderAgentToolCall` / `renderAgentToolResult` 返回组件的 `.render(width)` 断言行文本与宽度（含"宽 = 200/160/40"的多宽度断言）。
- UI 表面测试：直接用 `displayWidth` 断言"每行显示宽度 ≤ 上限"。
- 活动查看器测试：同样以渲染行断言为主要手段。
- 上述三类都是"通过公共渲染入口断言输出"的形态，本次沿用，不引入组件内部状态断言。

## Out of Scope

- **折行早停**（达到 `maxLines` 就停止折行）：会改变 `… (N more lines, …)` 提示中的精确行数，属于用户可见文案变更，单独评审。
- **宿主（pi）每帧全量渲染与虚拟化**：`renderLayoutFrame` 每帧重建布局与渲染缓存、scroll 子树全量渲染，属于上游问题；本次只把扩展侧占比压下去，剩余约 60 ms/帧不在本 effort 内。
- 活动面板、活动查看器、树 widget、活动缓存等其他渲染路径的优化（本次不触碰）。
- 为性能引入 CI 基准测试流水线（可后续单独提出）。
- 任何显示文案、行数上限、折叠提示、配色与布局的变化。
- 跨组件共享缓存或全局 memo。

## Further Notes

**取证方式（可复现）**

- 采集：以 Node 的 CPU profiler 参数启动 pi（`--cpu-prof`），在卡顿会话中做约 20 次缓慢按键 + 约 10 次滚轮，然后正常退出以落盘 `.cpuprofile`。
- 分析：按样本自耗时聚合函数，按 inclusive 时间归因到调用者；同时用"每次单动作的 CPU 毫秒数"独立交叉验证。
- 关键观测（一次 54 s 采样）：`(idle)` 占 67.9%（说明空闲真的不算），`doRender` inclusive 约 11.7 s，其中纯文本渲染组件 inclusive 约 9.2 s（79%），其下"逐字素折行 → 整串宽度测量"链路约 8.5 s；custom message 折叠渲染仅约 1.2 s（2%）。
- 交互实测：单次按键 290.6 ms、单次滚轮 271.9 ms（样本一致，说明"一次动作 = 一帧 = 约 280 ms"）。
- 交叉验证方式（改动后建议重复）：同一脚本测"10 次间隔 1 秒的按键/滚轮"的 CPU 总量除以 10。

**为什么最终用户会明显受益**

- 当前帧成本里 79% 是为"没有变化的内容"重复付费。缓存把稳态帧的这部分归零，用户感知就是"打字不用等、滚轮跟手"。
- 宽化原语修复让"内容刚更新、缓存未命中"的那一帧也便宜一个数量级，避免工具刚返回结果时的顿挫。

**风险与缓解**

- 脏缓存是唯一实质风险，因此失效条件被限定为两个显式入口（内容版本、宿主失效信号），并有专门的语义测试；同时"等价性基线"保证命中/未命中输出一致。
- 记忆化的宽度原语是纯函数变换，风险集中在"单字素等于整串测量"这一等价前提上，因此回归基线中特别覆盖 ZWJ emoji、组合标记与宽字符。
