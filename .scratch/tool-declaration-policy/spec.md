# Spec: 模板工具声明的语法边界与排除能力（tool-declaration-policy）

Status: ready-for-agent

## Problem Statement

模板作者在 `工具声明`（模板 `tools` 字段）上遇到三类问题，共同点是**无法从模板文本预测子代理的实际能力，失败也不指向模板**：

1. **含 `*` 的模板永远起不来。** 模板加载期本来就接受 `*`，也原样传给了子 pi；但子进程上报的 `活动工具集` 是 pi 展开后的**真实工具名**，扩展却拿它和字面量 `"*"` 比较，必然不等 → 子代理启动失败。失败信息只说"能力不匹配"，不指向模板，作者无从下手。

2. **含 `+`/`-` 的模板行为不一致且都不友好。** 新 pi 上，修饰符与普通名混用会让子进程直接 `exit(1)`，错误文案不指向模板；旧 pi 上 `+x` 被当作字面工具名静默忽略，作者以为加上了、实际没有。

3. **白名单不再排他。** pi 1.1.0 起，`工具声明` 里没列出的 MCP 工具不再被剔除，而是保留在子进程里，可经 codemode 一类间接路径调用（属于 `可达能力`）。模板作者写了"只给这些工具"，子代理实际却拥有更多能力，而模板**没有任何方式表达"排除"**。

第 3 点是这次兼容性审计（pi 0.99.1 → 1.1.0）暴露的真实行为变化；第 1 点说明扩展自己建模的比对逻辑会**打穿启动路径**——它没能发现第 3 点这类变化，却把 `*` 永久挡在门外。

## Solution

把 `工具声明` 的语法边界收窄到"白名单 + 通配"，并补上"排除"这条表达通道：

- 模板 `tools` 只支持**白名单写法**：纯工具名与 `*` 通配。含 `+`/`-` 修饰符的模板在**加载期**就被判为无效，诊断指向模板与字段。
- 含 `*` 的模板可以正常启动（不再被"字面集合相等"的比对拦下）。
- 新增**排除字段**：写进去的条目作为排除项传给子 pi，在工具注册阶段生效，间接路径同样看不到。
- 扩展**不再验证**子代理的 `活动工具集` 是否等于声明；该事实仍然上报并显示在活动面板上。
- 现有纯工具名模板与不写 `tools` 的模板行为完全不变。

## User Stories

1. 作为模板作者，我想只用工具名和 `*` 通配就能表达能力，以便不必理解 pi 的修饰符语法。
2. 作为模板作者，我想在模板里写了 `+`/`-` 时立刻收到指向模板与字段的错误，以便不用猜为什么子代理起不来。
3. 作为模板作者，我想 `*` 能出现在工具名的任意位置、可出现多次，以便表达"这一整类工具"。
4. 作为模板作者，我想用 `*` 一次覆盖某个 MCP 服务器的全部工具，以便不必逐个列举。
5. 作为模板作者，我想用排除字段表达"除了这些以外都要"，以便在保留宿主默认能力的同时拿掉特定工具。
6. 作为模板作者，我想排除项支持 `*` 通配，以便一次排除一整类工具。
7. 作为模板作者，我想排除项在工具注册阶段生效，以便子代理即使经 codemode 这类间接路径也看不到被排除的工具。
8. 作为模板作者，我想排除与白名单同时出现时行为明确（排除优先），以便不必猜优先级。
9. 作为模板作者，我想排除字段的非法形态（含逗号、内部空白、重复项、非字符串）在加载期被拒绝，以便错误尽早暴露。
10. 作为模板作者，我想排除字段为空数组时与不写它等价，以便不必关心空列表的特殊语义。
11. 作为模板作者，我想 `tools` 不写时行为完全不变（不动宿主默认工具集），以便已有模板不受影响。
12. 作为模板作者，我想纯工具名列表的行为完全不变，以便已有模板不受影响。
13. 作为模板作者，我想排除字段的名字形状规则与白名单一致，以便只需要记住一套规则。
14. 作为模板作者，我想模板编写文档明确写出"只支持白名单 + 通配"与"`*` 需要 pi ≥ 1.1.0"，以便知道边界在哪。
15. 作为父会话用户，我想含 `*` 的模板能正常派发子代理，以便使用更简洁的模板。
16. 作为父会话用户，我想扩展不再因为"活动工具集与声明不一致"而拒绝启动子代理，以便不再遇到莫名其妙的启动失败。
17. 作为父会话用户，我想子代理的 `活动工具集` 仍在活动面板上可见，以便我知道它实际拿到了什么工具。
18. 作为父会话用户，我想被排除的工具不会出现在子代理的活动工具集里，以便我看到的与实际一致。
19. 作为父会话用户，我想在旧 pi 上使用含 `*` 的模板时能从文档得知版本要求，以便区分"版本问题"与"配置错误"。
20. 作为扩展维护者，我想扩展对 pi 选择语义的建模只剩"判断是不是白名单模式"这一处，以便 pi 的版本演进不会打穿启动路径。
21. 作为扩展维护者，我想删除"活动工具集必须等于声明"的硬门禁，以便不再因为建模过期而拒绝启动子代理。
22. 作为扩展维护者，我想 `活动工具集` 仍然上报，以便观测能力不因删除门禁而丢失。
23. 作为扩展维护者，我想 `+`/`-` 不受支持的理由被记录在案，以便将来有人问"pi 支持而扩展不支持"时有据可查。
24. 作为扩展维护者，我想排除字段复用既有的字段解析与参数拼装机制，以便不引入新的校验路径。
25. 作为扩展维护者，我想本次改动不改动监督协议 wire 与协议版本，以便不需要迁移。
26. 作为扩展维护者，我想 `*` 的匹配语义完全交给 pi，不在扩展侧重复实现，以便不与 pi 的行为漂移。
27. 作为扩展维护者，我想测试只断言"模板文本进 → 解析结果/子进程参数出"这类外部行为，以便测试不绑定实现细节。
28. 作为子代理，我想我的能力边界由模板声明与排除共同决定，以便能力边界由模板作者控制。
29. 作为既有用户，我想升级扩展后不需要改任何现有模板，以便升级无成本。
30. 作为既有用户，我想那些今天本来就起不来的模板（含 `*` 或 `+`/`-`）在升级后要么能用、要么得到明确报错，以便不会更糟。

## Implementation Decisions

**模板发现模块**

- `工具声明` 解析后新增一步**选择模式判定**：任一条目以 `+` 或 `-` 开头 → 模板判为无效，新增与既有 `tools_invalid` / `reserved_tool` 同级的诊断码。
  - 理由：pi 的修饰符模式基准集来自**宿主的默认工具配置**，模板无法决定，因此"声明 = 实际"在原理上不成立；且新旧 pi 上的失败形态都不友好。
  - 判定完全照 pi 的规则（`+`/`-` 前缀即修饰符），只是把失败时机提前到加载期。
- `*` **不新增任何形状限制**：加载期继续接受，任意位置、多次出现均可。
- 新增**排除字段**（YAML 字符串数组），与 `工具声明` 共用名字形状校验：禁止内部逗号、禁止内部空白、禁止重复项、必须是非空字符串；与 `工具声明` 一样拒绝保留系统工具名（否则子进程会缺协议工具，并在启动时以能力不匹配失败）；同时加入模板字段白名单（否则未知字段会让模板整体无效）。
- 空数组与不写该字段**语义等价**（都不产生排除参数）。

**子进程参数拼装模块**

- 排除字段 → 子 pi 的排除参数，条目顺序与声明一致。
- 排除参数**无条件可用**：该参数在声明支持的最低 pi 版本上就已存在；旧 pi 不支持通配模式时该参数会静默无效，但那时白名单本来就会剔除 MCP 工具，叠加结果正确。
- `工具声明` 缺省时仍然**不传**白名单参数（既有语义：不写就不动宿主默认工具集）。
- 其余参数（会话、信任、扩展来源、上下文文件、思考等级、模型）行为不变。

**启动接受模块**

- **删除**"`活动工具集` 必须等于 `工具声明`"这条判定。
- 其余校验保持不变：协议工具集、系统工具来源路径、扩展路径身份、provider / model / thinking。
- `活动工具集` 仍由子进程上报，仍进入能力清单，仍供活动面板显示。

**协议与版本**

- 监督协议 wire 与协议版本**不变**（无帧结构变化）。
- pi 版本区间（`>=0.85.1`）**不变**。

**文档**

- 模板编写文档写明：`tools` 只支持白名单写法与 `*` 通配；`+`/`-` 不受支持并在加载期报错；`*` 需要 pi ≥ 1.1.0（旧版本把 `*` 当字面工具名，会得到零业务工具的子代理）；排除字段的用法与优先级。

**术语**

- 使用 `CONTEXT.md` 的 `工具声明`、`活动工具集`、`可达能力`。

## Testing Decisions

**什么算好测试**：只断言外部行为——"模板文本进 → 解析出的模板或诊断码出"、"模板进 → 子进程参数出"、"启动接受路径的接受/拒绝结果出"。不断言内部函数、私有结构或 pi 的匹配实现。

**S1 · 模板发现快照 seam**（既有：内存文件系统注入）

- `+x` / `-x` / 与普通名混用 → 模板无效 + 对应诊断码
- 纯名字列表、含 `*`（首/中/尾、多次出现）→ 模板有效
- 排除字段合法数组 → 进入解析结果；空数组 → 与不写等价
- 排除字段含逗号 / 内部空白 / 重复项 / 非字符串 → 模板无效
- 未知字段仍然让模板无效（回归）
- 既有纯名字模板用例全部保持不变（回归）
- 先例：既有 frontmatter 解析、字段白名单、无效候选诊断的用例

**S2 · 子进程参数拼装 seam**（既有：纯函数）

- 有排除字段 → 参数中出现排除参数且值与声明一致、顺序一致
- 排除字段为空数组或缺失 → 不出现排除参数
- `工具声明` 缺省 → 仍然不出现白名单参数（回归）
- 既有参数用例（扩展来源解析、扩展发现开关、思考等级等）保持不变
- 先例：既有扩展来源解析用例

**S3 · 启动接受 seam**（既有：注入假 pi RPC 客户端，**新增一条用例**）

- 假客户端上报的 `活动工具集` 与 `工具声明` **不同** → 子代理仍被接受启动（改动 2 的行为变更）
- 其余既有启动错误分类、协议故障用例保持不变
- 先例：既有启动错误分类与协议故障用例

**不做**

- 不为 `*` 写匹配单测（匹配由 pi 负责，扩展不再建模）
- 不断言 pi 侧的选择语义实现

## Out of Scope

- 恢复"未列名 MCP 工具不可达"的**自动**行为——本次只提供排除通道，是否排除由模板作者决定。
- 修饰符模式（`+`/`-`）的支持与自证。
- 启动诊断中携带子端实际 pi 版本。
- 通配条目"匹配 0 个工具"的告警。
- 能力清单字段的增删。
- 监督协议版本变更。
- pi 版本区间的调整。
- 模板字段的其它新增（如策略档位字段）。

## Further Notes

- **为什么不在扩展侧实现 `*` 的匹配**：pi 已经把 `*` 展开成真实工具名，扩展再实现一遍匹配只是重复建模，并且会随 pi 语义变化而失效。这次事故的共同根因就是"扩展用自己的一套模型去门禁 pi 的真实行为"——那套模型没能发现 MCP 保留注册的变化，却把 `*` 永久挡住。
- **跨版本风险**：`*` 在 pi < 1.1.0 上是字面工具名 → 匹配 0 个工具 → 子代理零业务工具但能正常启动（今天至少是启动失败）。缓解只有文档说明；"是否把子端 pi 版本放进启动诊断"留待后续决定。
- **与既有 ADR 的关系**：区域内没有相关 ADR（`docs/adr/0001` 是模型调用失败条目）。本决定属于"刻意偏离显然做法"的边界决定（pi 支持修饰符而我们不支持；pi 不校验结果而我们从今天起也不校验），建议单独记一条 ADR。
- **决策来源**：本 spec 综合自一次 pi 0.99.1 → 1.1.0 兼容性审计（结论：宿主加载、RPC、pi-tui、模板与启动参数面均无破坏性变更，唯一风险面是 `--tools` 语义）与随后的设计讨论。
