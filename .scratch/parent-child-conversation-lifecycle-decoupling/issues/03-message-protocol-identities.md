# 连续会话消息的最小协议与身份元数据

Status: resolved
Type: grilling
Blocked by: 01

## Question

在把父子交流建模为持续会话后，`message_id`、`task_id`、`turn_id`、`commit_id` 是否全部从扩展内部和父子协议中移除，还是保留其中一部分作为不可见的传输元数据？如果移除，如何替代当前邮箱主键、迟到回合识别、final 去重和结果关联；如果保留，分别证明每个字段仍承担的最小职责。决策还必须明确普通消息、final_report、控制消息的关联边界，不能让这些字段重新成为生命周期状态或用户工作流概念。

## Answer

四个应用层字段 `message_id`、`task_id`、`turn_id`、`commit_id` 全部从本 effort 的扩展内部、父子协议、工具返回、父端通知和状态投影中移除：

- `message_id` 不再为不存在的插件 mailbox 或派发队列分配；`send_message` 直接同步交给 Pi，成功只返回接纳结果。
- `task_id` 不再作为持续会话消息、报告、控制帧或生命周期事件的路由键；本 effort 不建模任务或任务结果，不能从消息恢复任务租约。
- `turn_id` 不再用于识别“当前/旧回合”或拒绝持续会话中的普通消息和报告；Pi 回合边界由生命周期事实表示，消息调用结果由接收侧 Pi 同步返回。
- `commit_id` 完全删除；取消自动 final 后不存在 prepared/accepted final 两阶段提交，也不存在同 turn 首个 final 覆盖规则。

`agent_id` 保留在子代理上行信封和监督身份校验中，用于确认来源、直接父范围和父端展示；它是节点身份，不是任务或用户工作流身份。监督协议自身的底层帧元数据、快照重同步 `request_id`、控制请求/响应 `operation_id` 可以按各自协议需要保留，但不进入消息语义、生命周期状态、任务所有权或 `wait_agent` 业务结果。消息发送不依赖应用级序列、ACK 或窗口。

上行信封明确分为 `kind: "message"` 和 `kind: "final_report"`，两者只表达普通父子消息与显式报告事件的区别；`final_report` 不携带运行状态、任务结果或 commit 字段。每次调用都独立同步交给接收侧 Pi；控制请求/响应和生命周期故障通知仍走各自独立协议域，不伪装成报告。

每次消息调用都由接收侧 Pi 独立同步裁决；成功调用交给 Pi 处理并登记相应会话事件，失败只返回本次发送错误。同一正文的再次调用是新的事件；本 effort 不定义应用层序列、重复/迟到裁决、ACK、发送窗口或应用消息重放。

`task_assignment` 和 `task_started` 这类依赖四个应用层字段的监督帧删除。真实 Pi 回合开始进入生命周期事实流；`wait_agent` 按子代理和独立事件/状态投影观察，不依赖消息 ID、任务 ID、回合 ID 或提交 ID；它不返回任务结果或 `last_task`。

消息身份、传输细节和父端接纳的完整边界由本票及后续并发决策共同确定；本票锁定应用层身份字段全部删除、消息逐条同步接纳以及控制/生命周期协议域分离。

## Amendment

后续并发决策覆盖本答案中关于监督层 ACK 的部分；更后续的并发决策又取消了消息事件的顺序语义：`reply_seq` 不进入消息信封或会话模型，不用于 FIFO、重复、迟到、冲突或窗口裁决。底层 `stream_id`/帧序号如因传输实现保留，也只是连接和帧完整性元数据。父子之间的每次消息发送都通过同步的逐条 Pi 接纳响应返回成功或 `message_delivery_failed`，不使用 ACK、应用发送窗口或应用消息重放；同一正文的再次调用是新事件，响应未知不自动重试，消息失败不改写健康子代理的生命周期。
