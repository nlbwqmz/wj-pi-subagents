# 持续会话中的消息顺序与并发操作

Status: resolved
Type: grilling
Blocked by: 01, 02, 03, 04, 06

## Question

父代理在旧回合停止后立即发送新消息、子代理在同一时间发送 final_report 或普通回复、父端正在 interrupt/terminate 时，消息应如何排序和裁决？需要在不依赖僵化任务概念的前提下，定义同一会话的顺序保证、发送队列、旧消息/迟到消息的处理和控制操作优先级；特别要保证已产生的 final_report 不被后来的父消息越过，同时发送失败不会永久锁死健康子代理。

## Answer

本票据最终取消消息级排序、业务发送队列和替代性的会话协调器。此前提出的方向内 FIFO、`reply_seq`、迟到/重复裁决和跨方向“越过”规则均不进入最终规格；Pi 自身如何排队或处理输入属于本 effort 之外。

### 同步发送

`send_message`、`normal_reply` 和 `final_report` 都是独立的同步接纳操作：调用接收侧 Pi 的消息接口，正常返回即成功，抛错、明确拒绝或响应未知即返回稳定的发送错误。调用方不等待模型读取、Pi 回合收束、context/UI 观察或任何监督层 ACK。消息路径不使用 transport ACK、reply ACK、累计确认、发送窗口或应用消息重放。

每次调用的成功结果只说明正文已交给接收侧 Pi；它不表示后续模型处理完成，也不改变子代理生命周期。Pi 内部的 steer/follow-up 队列和处理顺序不进入会话模型。相同正文的再次调用是新的消息事件。

### 报告与并发

`final_report` 成功调用 Pi 后即交由 Pi 处理，不再由扩展建立“最终报告优先级”、结算或排序屏障。它不结束 Pi 回合或会话；后续消息与该调用之间不建立扩展层的相对顺序、优先级、撤销或覆盖规则。报告调用失败时不产生父端可见的报告事件，正文不暗存、不自动重试。

消息信封不携带 `reply_seq` 或其他应用级排序/去重身份。底层实现若因帧完整性或连接管理保留 `stream_id`、帧序号等元数据，它们不进入消息语义、`wait_agent` 结果或生命周期状态。

### 控制与屏障

`interrupt_agent` 和 `terminate_agent` 也采用同步控制接纳响应。控制屏障只拒绝屏障建立后新发起的消息、报告和续跑；已经被 Pi 接纳或已经进入接纳裁决点的数据不回滚。响应未知时调用方不猜测状态，后续真实生命周期事实由唯一生命周期权威归约；终止屏障不可逆，并可升级已有的中断屏障。控制结果不由消息成功或失败推断。

上下文一致性屏障同样只拒绝新的发送调用，不改变已经被 Pi 接纳的事件；压缩或重连不自动重放应用消息。发送失败只结算本次调用并释放本地进行中资源，健康子代理保持原生命周期；Pi 可用后后续显式调用可以继续。迟到或重复的消息不在本 effort 建立额外的应用层裁决规则。

### wait_agent 投影

每次成功接纳的 `reply`、`final_report` 和 `idle`/终止/故障事实分别独立唤醒 `wait_agent`；如果没有新的事件而目标已经处于稳定 `idle`、`failed` 或 `terminated`，则立即返回当前快照。父端每个 `turn_start` 建立内部观察水位，回合开始前已经进入父会话的通知不会在后续等待中重复返回，回合开始后新到达的通知仍保留给当前回合内的等待。返回的会话事件与生命周期快照保持独立。并发事件的到达顺序不是公开契约，生命周期状态不能把已经接纳的会话事实推断成任务结果或覆盖为另一种消息结果。
