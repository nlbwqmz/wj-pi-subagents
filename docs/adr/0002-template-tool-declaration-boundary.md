# 模板工具声明只支持白名单形式，且扩展不对活动工具集做结果门禁

模板的 `工具声明` 会被原样翻译成 pi 的 `--tools` 参数。pi 的 `--tools` 是一门选择表达式语言：支持通配 `*`、支持 `+name` / `-name` 修饰符；并且 pi 1.1.0 起不再用白名单剔除未列名的 MCP 工具，而是把它们保留注册，可经 codemode 一类间接路径调用（属于 `可达能力`）。

我们决定把扩展与这门语言的关系定在三条边界上：**(1) 只接受白名单写法**——含 `+` / `-` 的模板在加载期判为无效，因为修饰符模式的基准集来自宿主的默认工具配置，扩展无法保证"声明 = 实际"；**(2) 不自动恢复 pi 1.1.0 之前的 MCP 剔除行为**，改为提供排除通道（在工具注册阶段生效，间接路径也看不到），是否排除由模板作者决定；**(3) 删除"`活动工具集` 必须等于 `工具声明`"的结果门禁**——该事实仍上报并进入能力清单，但不再阻断启动。

共同的理由是：**扩展只判断"这个写法我能不能负责"，不重建 pi 的选择结果**。此前扩展用自建的一套模型去门禁真实行为，结果既没能发现 MCP 保留注册这次真实变化，又让含 `*` 的模板永久无法启动——建模越少，越不容易被 pi 的版本演进打穿。

## Considered Options

- **接受修饰符模式，把自证降级为"`+x` 生效、`-x` 不生效"**：基准集来自宿主 `settings.json` 的默认工具配置，同一个模板在不同机器上给子代理不同能力，"声明 = 实际"在原理上不成立；失败模式（子代理能力随宿主配置漂移）极难排查。
- **要求作者显式 opt-in（新增策略档位字段）**：新字段 + 文档 + 测试的成本，换来的仍是"不可证明"，只是把风险显式化。
- **用协议事实补齐自证（子端上报基线工具集，父端校验基线 ± 修改）**：只能证明"子端自洽"，不能证明"与模板一致"，却要扩协议面。
- **把结果门禁降级为告警而不是删除**：仍需维护一套对 pi 语义的建模，模型过期时表现为误报噪音；`*` 是否可用仍然取决于该模型是否正确。
- **自动注入排除项，恢复 pi 1.1.0 之前的剔除行为**：会改变所有既有白名单模板的行为、与 pi 的设计意图相反，且需要硬编码 pi 的 MCP 资源工具名。
- **用 `--no-mcp` 实现严格模式**：该参数是 pi 1.1.0 新增，旧版本不识别，等于强制抬高支持下界。
- **加载期拒绝 `*`**：会让扩展继修饰符之后再偏离 pi 语法一次，而 `*` 属于白名单模式、语义明确。

## Consequences

- 含 `*` 的模板首次可用；但它们在 pi < 1.1.0 上会被当作字面工具名，得到**零业务工具**的子代理（今天至少是启动失败）。缓解只有文档说明。
- 拼错的工具名不再被拦下，子代理会静默少一个工具——与 pi 自身的行为一致。
- 修饰符写法在扩展内永久不可用，作者需要用白名单表达同样的意图。
- 白名单不再排他这一事实被接受；想要排他的模板作者必须自己声明排除项。
- 不影响监督协议 wire 与协议版本，也不改变 pi 版本支持区间。
- 领域语言随之更新：`工具声明`（只承诺活动工具集）、`活动工具集`、`可达能力` 进入 `CONTEXT.md`。

详细验收边界见 `.scratch/tool-declaration-policy/`。
